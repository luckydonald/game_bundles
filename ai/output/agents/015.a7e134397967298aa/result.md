This confirms end-to-end: one raw offer title ("TMNT: Splintered Fate + Metalhead DLC") becomes exactly one `Game` entry (`name: 'TMNT: Splintered Fate'`, note the resolver's exact-title-match search apparently found/normalized to the base game only) with a single `ids: [steam:2996040]` — the DLC portion is silently dropped, not modeled as a second id or second Game.

## Summary

**1. Tier/offer discovery** (`crawler.py`): `crawl_humble_offers` (L144-213) fetches either explicit `--url` targets or discovers the current Choice page (`CHOICE_URL`) plus every active Games bundle from `parse_bundle_index` (`BUNDLES_URL`). Parsing happens in `parser.py`: `parse_bundle_page` (L352-455) builds `HumbleTier` objects (cumulative, ordered by `bundle_data.tier_order`) each holding a list of `HumbleItem`; `parse_choice_page` (L499-611) builds one flat `HumbleTier`. The raw offer shape is `HumbleItem` (`models.py` L42-65): `machine_name`, `title`, `item_type`, `is_game`, price, `redeem_on` (store list), plus a `resolution: HumbleResolution` (`ids`, `unresolved_stores`) filled in later. **There is no sub-item/DLC decomposition anywhere** — a title like `"TMNT: Splintered Fate + Metalhead DLC"` is just one `HumbleItem.title` string; nothing splits it into a base game + DLC.

**2. Title → Steam ID resolution** (`resolver.py`): `StorefrontResolver.resolve_item` (L208-245) searches each store in `item.redeem_on` via `STORE_SEARCH_URLS`, keeps only candidates whose `normalized_title(candidate.title) == normalized_title(item.title)` (exact match after case/punctuation/trademark normalization — `sources/storefronts.py`), and takes it automatically if exactly one; otherwise prompts via `CandidateChooser` or records `unresolved:source:humblebundle:<machine_name>`. `resolve_archive` (L247-299) dedupes by `machine_name` across tiers and writes results back into `HumbleResolution`. **Grepped for "multi"/"compound"/"+"/"DLC"/"bundle" special-casing — none exists.** A compound title like "X + Y DLC" or "Frostpunk: Game of the Year edition" is resolved as one literal search string; it only "succeeds" when the storefront happens to have an exact-title match for that whole string (rare) or falls to manual/`unresolved` review. There's no concept of "this offer maps to N storefront items."

**3. Offer → `Game` (writer)** (`crawler.py` `write_humble_offer`, L247-352): for each tier, iterates `tier.items`, skips non-games and duplicate resolved ids already seen (`seen_ids`), and does `games.append(Game(name=item.title, ids=item.resolution.ids))` (L312, similarly L274 for Choice pools) — strictly **one `HumbleItem` → one `Game`**, `ids` = whatever `resolution.ids` produced (0+ store ids, or the `unresolved:...` marker). `render_game_list_yaml` (`sources/common.py` L72-79) just serializes `GameList`/`Game` via Pydantic + YAML; it has no game-splitting logic, it's purely a renderer. `models.py`'s `Game.ids: list[str]` *can* hold multiple qualified ids (e.g. `steam:X`, `gog:Y`) — that's used for the same game across multiple storefronts, not for splitting one title into multiple products.

**4. Archives**: `archives/humblebundle/{choice,bundle}/<key>/{metadata.json,source.json}` store the full `HumbleArchive` (post-resolution) and raw payload. There is **no field or nesting anywhere in `HumbleItem`/`HumbleResolution`/`HumbleTier`** for "this offer resolved to N storefront items" — it's strictly 1 offer → 1 `resolution.ids` list → 1 `Game`.

**5. Tests**: `tests/test_humblebundle_resolver.py`, `test_humblebundle_parser.py`, `test_humblebundle_crawler.py` — all exercise single-title exact/ambiguous/unresolved matching; none test compound titles or multi-item splitting.

**Where multi-item support would need to be added**: (a) `resolver.py`'s `resolve_item`/`resolve_archive` would need to detect compound titles (e.g. split on `" + "`, or a "GOTY/Definitive Edition" pattern) and produce either multiple `HumbleResolution.ids` entries or a genuinely new concept of "sub-items"; (b) `HumbleItem`/`HumbleResolution` (`models.py`) would need a field to carry N resolved storefront entries with their own display names, since currently `resolution.ids` is just a flat list of ids for *one* game, not distinguishable sub-products; (c) `write_humble_offer` (`crawler.py` L268-317) would need to emit multiple `Game` entries per `HumbleItem` when it has multiple sub-resolutions, rather than the current strict 1:1 `Game(name=item.title, ids=item.resolution.ids)`.
