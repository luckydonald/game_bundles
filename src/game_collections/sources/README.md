# Sources

A "source" scrapes a public storefront/bundle page into launcher-neutral `lists/` entries plus a normalized `archives/` record, as opposed to `launchers/`, which synchronizes already-owned lists into a launcher library. `common.py` holds the file-writing helpers shared by every source (`atomic_write`, `dump_json`, `render_game_list_yaml` — temp file + `fsync` + rename, deterministic sorted JSON, and the YAML list renderer with its IDE schema comment) plus `load_cached_archive`, the resume-from-disk helper all four sources use (see below). `storefronts.py` holds `StoreName`/`STORE_ROOTS`/`STORE_HOSTS`/`parse_store_identity`/`match_store`/`normalized_title` — parsing a storefront URL (Steam/GOG/Epic/Ubisoft/Humble Store) into a qualified ID or comparing two titles — shared by any source that needs it, independent of whichever source package first needed it. It also holds `qualified_ids_from_urls`/`is_known_store_url`/`EXTRA_STORE_PARSERS` — a wider, ITAD-only extension for storefronts with no launcher-sync relevance (Microsoft Store, 2game, ...), each added only once a real deal redirect has confirmed its URL shape; an unmatched shop is skipped, never guessed. Humble Bundle, DailyIndieGame, Green Man Gaming, and isthereanydeal are the four implemented sources.

### Progress logging, incremental writes, and resuming

`crawl_humble_offers`/`crawl_dig_offers`/`crawl_gmg_offers`/`crawl_itad_offers` all accept:

- `log: Callable[[str], None]` — called with human-readable progress lines as the crawl runs ("Bundle x/y: ...", "Offer x/y: ...", "  Game x/y: ..."), so the CLI can print `typer.echo` output live instead of staying silent until the whole crawl finishes. Defaults to a no-op so existing calls/tests are unaffected.
- `on_offer: Callable[[CrawledOffer], None] | None` — called immediately once each offer/bundle finishes processing, so the CLI writes it to disk right away (`write_dig_offer`/`write_humble_offer`, plus `write_resolution_map` for Humble) instead of batching every write until the whole crawl completes. A crash or interrupt partway through only loses the in-flight offer, not everything already done.
- `archive_root: Path | None` — when given, enables resume-from-disk: before doing the expensive part of a target, `sources.common.load_cached_archive(ArchiveModel, metadata_path, source_path)` is tried first. A hit (valid JSON, and the archive still validates against the current `schema_version`) skips the expensive work entirely and reuses the cached, already-processed result. A schema bump makes old cache entries fail validation automatically, so stale cache is never silently trusted — it just falls through to a real fetch. Passing `archive_root=None` (what `--refresh`/`--no-cache` does on every `scrape` command) disables this and forces everything to be redone.

The four sources skip different amounts of work on a cache hit, because of what's knowable before any fetch happens:

- **DailyIndieGame**: bundle numbers are known upfront (from the index page or explicit `--url`), so a cache hit skips the bundle-page fetch *and* every per-game listing-page fetch for that bundle — the biggest win, since each is a full headed-browser page load and most bundles in a discovery-mode run were already scraped last time (bundles roll off/on gradually, hence the overlap).
- **Humble Bundle**: the cache key depends on parsed fields, so the page itself is always fetched — but a cache hit skips `StorefrontResolver.resolve_archive`, which is the actually expensive part (one storefront search per distinct game).
- **Green Man Gaming**: bundle slugs are known upfront (from the index page or explicit `--url`), so a cache hit skips the bundle-page fetch, every per-item product-fragment fetch, *and* `StorefrontResolver.resolve_archive` — the same two expensive stages DailyIndieGame and Humble each separately skip, combined, since this source needs both a per-item enrichment fetch (DRM label, needed before resolution can pick a store) and title-based resolution.
- **isthereanydeal**: bundle ids are known upfront from the (always-fetched) discovery API, so a cache hit skips only the per-bundle detail-page fetch/parse — there's no separate resolution stage here since storefront IDs are read directly off the detail page, not searched for.

## Humble Bundle (`humblebundle/`)

Backs `game-collections scrape humblebundle`. Pipeline:

- `crawler.py` — `HumbleHttpClient` (small retrying `httpx` client for public HTML) and `crawl_humble_offers(...)`, which either fetches the explicit `--url` list or discovers the current Choice month (`CHOICE_URL`) and every active Games bundle from the bundle index (`BUNDLES_URL`); see "Progress logging, incremental writes, and resuming" above for its `log`/`on_offer`/`archive_root` parameters. `write_humble_offer(...)` then atomically writes (via `sources.common.atomic_write`) the normalized `archives/humblebundle/.../metadata.json` + `source.json`, and one `lists/humblebundle/...` YAML per advertised cumulative tier (`choice/YYYY-MM.yml`, or `bundle/<key>/<n>-item-bundle.yml` with `entire-<n>-item-bundle.yml` for tier 0).
- `parser.py` — extracts the embedded JSON payload from Humble's page HTML (`parse_choice_page`, `parse_bundle_page`, `parse_bundle_index`) into a `HumbleArchive` plus the raw source payload; converts descriptions to Markdown.
- `resolver.py` — `StorefrontResolver` matches each Humble product title against real storefronts (Steam, GOG, Epic, Ubisoft, Humble Store) via `STORE_SEARCH_URLS`. Unique exact matches resolve automatically; ambiguous matches prompt for a candidate or canonical URL/ID (or record `unresolved:source:humblebundle:<machine-name>` under `--non-interactive`). Reviewed decisions persist in `config/humblebundle-store-ids.yml` (a `HumbleResolutionMap`) so re-running the scraper doesn't re-prompt for already-resolved titles. `resolve_archive(...)` also takes a `log` callback, called once per distinct game it resolves ("  Game x/y: ...") — the only place that knows the per-game count during resolution. For the `steam` provider specifically, `_search_steam` tries `store.steampowered.com` first (cheap, no browser) and only falls back to `steamdb.info`'s own app search — often better at finding the exact product for a noisy Humble title — when steampowered.com doesn't already give a unique exact-title match. steamdb.info sits behind a Cloudflare *managed* (Turnstile-class) challenge, confirmed live to defeat plain `httpx`/`curl`, TLS-fingerprint impersonation (`curl_cffi`), and JS-VM challenge solvers (`cloudscraper`, in both its PyPI release and a third-party fork) alike — only a real headed browser session passes it, same situation as `dailyindiegame`'s Cloudflare challenge below. `steamdb.py`'s `SteamDbBrowserClient` (a `patchright` headed persistent context, mirroring `dailyindiegame.crawler.DigBrowserClient`) is only launched lazily on the CLI's first actual fallback use (see `cli._LazySteamDbFetcher`), so a run where steampowered.com resolves everything never pays the browser-launch cost; if the browser can't launch at all (missing `patchright`, headless CI runner, ...), the CLI logs a warning and every later `steam` lookup just falls back to steampowered.com-only for the rest of the run.
- `models.py` — `HumbleArchive`/`HumbleItem`/`HumbleResolution`: the strict Pydantic shape of the normalized archive, validated against `schemas/humblebundle-archive.schema.json`.

`scripts/backfill_humble_choice.py` is a standalone script (not part of this package) that reuses these same crawler internals (plus `sources.common`) to backfill historical Choice months from a third-party mirror, since Humble's own site only exposes the current month to guests.

### Scheduled scraping

`.github/workflows/weekly-humblebundle-scrape.yml` runs `game-collections scrape humblebundle --non-interactive` every Monday (plus manual `workflow_dispatch`) and opens/updates a pull request with any new offers. It reuses a single rolling branch (`automation/humblebundle-weekly-scrape`) across weeks — rebasing it onto `main` if it survived from last week's still-open PR, or recreating it from `main` if last week's PR was merged/closed — and never fails the job on unresolved storefront IDs, since those are an expected, committable state for later manual `game-collections complete` follow-up.

## DailyIndieGame (`dailyindiegame/`)

Backs `game-collections scrape dailyindiegame`. This source differs from Humble in three ways worth knowing before touching it:

1. **The site sits behind a Cloudflare managed challenge.** Plain `httpx`/`curl` get an instant 403. Worse, a stock **headless** Playwright/Chromium session (even the `patchright` fork built specifically to evade bot detection) hangs on the challenge page forever — Cloudflare fingerprints CDP-driven headless automation and never resolves it. Only a **headed** `patchright` persistent context (`headless=False`, a real, non-headless Chromium) actually passes the challenge; this was confirmed against the live site, not assumed. `DigBrowserClient` in `crawler.py` implements this: `chromium.launch_persistent_context(user_data_dir, headless=False, no_viewport=True)`, then polls the tab title (skipping past `"Just a moment..."` and the post-challenge `"Loading ..."` redirect) rather than trusting `wait_until="networkidle"` — this site's persistent connections mean network never truly idles, so a bounded `wait_for_load_state("networkidle", ...)` is used as a best-effort settle step only, always followed by a fixed extra wait. A GitHub Actions runner (or any other unattended/headless-only environment) may not be able to run this at all — there is currently no scheduled workflow for this source (unlike Humble's) for exactly this reason.
2. **No resolver needed.** Every game on a bundle page links directly to `https://store.steampowered.com/app/<id>` — the Steam AppID is already given in the page, so there's no title search/matching/resolution-map/`unresolved:*` machinery like Humble's `StorefrontResolver`. This source only ever produces `steam:<id>` IDs.
3. **No structured dates or fixed bundle-name format.** There's no embedded JSON or `<time>`/meta date anywhere; the only signal is a live countdown string (`"Bundle ends in D days : HH : MM : SS"`), parsed relative to the crawl timestamp. The bundle's display name isn't one fixed literal either — it varies by promotion (`"DIG Bundle <N> - ADULT"`, `"FRIDAY BARGAIN <N>"`, and presumably others not yet seen) — so the parser reads it from the first `<span class="DIG-contentOrangeBIG">` on the page (a stable marker across naming schemes) rather than matching a specific prefix, and derives `is_adult` from whether that text contains `"ADULT"`.

Pipeline pieces:

- `models.py` — `DigArchive`/`DigItem`/`DigPrice`/`DigDates`: flatter than Humble's shape since there's one flat price tier per bundle (not cumulative tiers) and no resolver-produced fields.
- `parser.py` — `parse_bundle_index_page` (weekly-bundle numbers from the `site_content_bundles.html` gallery), `parse_bundle_page` (title span, price-summary sentence, countdown, per-game Steam links via a small `<td>`-tracking `HTMLParser`), `parse_game_listing_page` (each game's own `site_gamelisting_<id>.html` for price/region/description/cover art).
- `crawler.py` — `DigBrowserClient` (see above), `crawl_dig_offers(fetch, ...)` takes an **injectable `fetch` callable** exactly like Humble's crawler (plus `log`/`on_offer`/`archive_root`, see above), so every test exercises real parsing/orchestration logic with a fake `fetch` and never launches a browser; only the CLI wires in the real `DigBrowserClient.fetch`. `write_dig_offer(...)` writes `archives/dailyindiegame/bundle/<N>/{metadata.json,source.json}` and `lists/dailyindiegame/bundle/<N>.yml`.

## Green Man Gaming (`greenmangaming/`)

Backs `game-collections scrape greenmangaming`. Notable differences from the other two sources:

1. **Two domains, both plain server-rendered HTML.** The bundle index lives at `greenmangaming.com/bundles/` (an Angular app, but the bundle grid itself is rendered server-side into a `<div class="product-grid">`, not fetched via an API call); each bundle's own pages live on a *different* domain, `greenmangamingbundles.com` (a separate Django + htmx app). Neither needs a browser or hits a bot challenge — plain `httpx` GETs work for everything, including the htmx product-detail fragment (fetched with an `HX-Request: true` header, same as the real frontend would send).
2. **Resolver-based ID matching, like Humble.** Bundle pages never link straight to a storefront ID — only a free-text DRM label per item (`<dt>DRM</dt><dd>Steam</dd>`, fetched from that item's own `/bundles/<slug>/product/<id>/` fragment). `resolver.py` mirrors `humblebundle/resolver.py`'s `StorefrontResolver`/store-search machinery (re-exported from it, not reimplemented) with a `redeem_on_for_drm` mapping (`Steam`→`steam`, `GOG`→`gog`, `Uplay`/`Ubisoft Connect`→`ubisoft`; anything unrecognized is left unresolved rather than guessed).
3. **Cumulative tiers derived from the default page render, no extra requests.** A bundle detail page's default render shows every item across every tier "unlocked" at once, and each item's `hx-vals` attribute (used by the site's own tier-switching htmx interaction) already tags it with the *tier it was originally unlocked at* (`tier_name`). `parser.py` groups items by that tag and accumulates them in ascending tier-price order to build each cumulative tier — this was cross-checked against the live site's `/bundles/<slug>/switch_tier/` endpoint (which returns exactly the same cumulative sets per tier) before trusting it, so no extra per-tier fetch is needed, unlike DailyIndieGame's per-game listing-page fetches.

Pipeline pieces:

- `models.py` — `GmgArchive`/`GmgTier`/`GmgItem`/`GmgPrice`/`GmgResolution`: cumulative tiers like `HumbleArchive`/`HumbleTier`, but flatter items (no `is_game`/bonus distinction — every item observed in a GMG bundle is a purchasable product, DLC included).
- `resolver.py` — `StorefrontResolver`/`GmgResolutionMap`/`redeem_on_for_drm`, importing `STORE_ROOTS`/`StoreName`/`parse_store_identity`/`normalized_title` from `sources.storefronts` and `STORE_SEARCH_URLS`/`StoreCandidate`/`parse_store_candidates` from Humble's resolver instead of duplicating them. Reviewed decisions persist in `config/greenmangaming-store-ids.yml`. Mirrors Humble's steampowered.com-first, steamdb.info-fallback `_search_steam` behavior for the `steam` provider too (see Humble Bundle's resolver section above), importing the shared `STEAMDB_SEARCH_URL`/`parse_steamdb_results`/`SteamDbBrowserClient` pieces from `humblebundle.steamdb`.
- `parser.py` — `parse_bundle_index_page` (video-games-category bundle slugs from the index page's `product-card`/`cta-button` markup), `parse_bundle_page` (title, currency, and cumulative tiers per the tier-grouping approach above), `parse_product_fragment` (DRM/platform/developer/publisher/description from one item's htmx fragment).
- `crawler.py` — `GmgHttpClient` (bounded-retry `httpx` wrapper, sends `HX-Request: true` so product-fragment fetches work), `crawl_gmg_offers(fetch, resolver, mapping, ...)` takes the same **injectable `fetch` callable** plus `log`/`on_offer`/`archive_root` conventions as the other sources. `write_gmg_offer(...)` writes `archives/greenmangaming/bundle/<slug>/{metadata.json,source.json}` and one `lists/greenmangaming/bundle/<slug>/<tier-id>.yml` per cumulative tier.

## isthereanydeal (`isthereanydeal/`)

Backs `game-collections scrape isthereanydeal`. This source is structurally different from the other three: it's a bundle *aggregator*, not a bundle seller, so it discovers bundles hosted on many different platforms and writes into each one's own `lists/<provider>/` directory rather than a single `lists/isthereanydeal/` tree — `archives/isthereanydeal/...` is the only thing that's always this source's own.

1. **Discovery needs a plain anonymous bootstrap, not a resolver.** `GET https://isthereanydeal.com/bundles/` sets a `sess2` session cookie and embeds a matching CSRF-style token plus a shop-id→name table in an inline `var g = {...}` script (`parser.parse_bootstrap_page`). That token is then sent as the `itad-sessiontoken` header on `POST /bundles/api/list/?tab={live,expired,pending}` (`{"offset": N, "sort": null, "filter": null}`, paginated by 30 until `"done": true`) — a request missing the header, or one whose `Accept` isn't `application/json`, gets routed to the HTML fallback page or a `400`. None of this involves any real account; it's the same anonymous bootstrap any visitor's browser performs.
2. **The list API's own embedded tier/game preview is deliberately not modeled.** Each summary entry also carries a `tiers` array with ITAD-internal game ids/slugs/asset URLs/shop-key numbers — a higher-churn duplicate of what the bundle's own detail page gives with real storefront IDs, and unused here. `parser.parse_list_page` strips it (`_without_tiers_preview`) before validating the rest through `ItadListSummary`, so the archive's `source.json` stays strict (fails loudly on any *other* unexpected field) without being brittle against that specific blob's asset/platform/type enum churn.
3. **Tiers and per-game storefront IDs come from the detail page's own embedded JSON, not DOM scraping.** Every `GET https://isthereanydeal.com/bundles/<id>/` (server-rendered HTML) carries a shared inline `<script>` declaring both `var g = {...}` (token/shops config) and `var page = ["Bundle", {"liveData": {"tiers": [...]}}];` (this page's own SSR'd state) — confirmed live, the same script tag on every page. `parser.parse_bundle_detail_json` is the primary parser: `liveData.tiers` is a list of **per-tier-exclusive** (not cumulative) `{"price": [cents, "CUR"] | null, "note": ..., "games": [...]}` entries, so it accumulates each tier's `games` onto a running cumulative list to reproduce `ItadTier.items`'s expected cumulative shape (confirmed against a live 3-tier GreenManGaming-hosted bundle: 2/2/2 exclusive games per tier summed to its known 6-game total). Tier display names come from `tier.note` when the provider sets one (confirmed `"Bronze"/"Silver"/"Gold"` for GreenManGaming), falling back to the dedicated Humble scraper's own `entire-{n}-item-bundle`/`{n}-item-bundle` convention for Humble-provider bundles (which never carry a `note`), or a generic `Tier N` otherwise. Each game's storefront IDs come from its `reviews[].url` entries (`{"source": "Steam", "url": "https://store.steampowered.com/app/<id>/"}`) via the shared `sources.storefronts.parse_store_identity` — no resolver/title-search needed, and this works identically for mature-rated bundles (confirmed live: the mature-content gate only hides the page's *rendering*, not this embedded data). Not every game has a recognized link (confirmed live: some IndieGala/Fanatical bundles leave several games with no direct storefront link at all); those get `unresolved:source:isthereanydeal:<bundle-id>:<game-slug>`. `parser.parse_bundle_detail_page` is a DOM-based fallback (BeautifulSoup, not regex) covering the rare case where the embedded JSON is missing or malformed — `crawler.crawl_itad_offers` tries the JSON path first and only falls back to it (logging a note) on `None`/a parse failure; kept intentionally rather than removed, as a hedge against ITAD ever dropping that script.
4. **A reviewed shop table corroborates resolved ids, never resolves them by itself.** `config/isthereanydeal-shops.yml` (`shop_config.load_shop_config`, `schema: 2`) lists every ITAD shop as `{name, id, slug}` — `id` mirrors the bootstrap script's shop-id table (`61: Steam`, `35: GOG`, etc; two entries, App Store/Google Play, have no ITAD shop id at all), `slug` is the qualified-id prefix once that shop's storefront URL shape has been verified (see `sources.storefronts`). Each game's `keys` (shop-id ints) are compared against the provider(s) its `reviews[].url` actually resolved to, purely to log a one-line mismatch warning — resolution itself is always URL-based, via `sources.storefronts.qualified_ids_from_urls`, which recognizes more than just the original 5 launcher stores (Microsoft Store, 2game, ...); an unverified shop's deal/review link is simply skipped, not guessed.
5. **Provider-slug resolution and dedup, not a resolution map.** `page.name` (the aggregator's label for the bundle's origin platform, e.g. `"GreenManGaming"`, `"Fanatical"`) maps to our `lists/<provider>/` directory name via a small reviewed `config/isthereanydeal-providers.yml` (`provider_config.resolve_provider_slug`; an unreviewed provider falls back to a slugified name with a logged warning instead of failing). The bundle's real, provider-native slug is decoded from its affiliate-redirect `url` field (`parser.real_provider_slug` — handles the `u=`/`ued=` wrapper conventions seen so far, or the unwrapped URL directly for providers like IndieGala that don't redirect at all). Before writing `lists/<provider>/...`, `crawler.write_itad_offer` substring-matches that slug against every existing path under `lists/<provider>/` (Humble's own directories are date-prefixed, hence substring rather than exact) and skips the list write entirely if anything already covers it — the archive record is still always written.
6. **The per-game detail-page solver is a separate, on-demand follow-up, not part of the crawl.** Games with no recognized storefront link on the bundle detail page get `unresolved:source:isthereanydeal:<bundle-id>:<game-slug>`; `game-collections complete FILE --provider isthereanydeal --mode unresolved` resolves these later by fetching that game's own `https://isthereanydeal.com/game/<slug>/info/` page (`parser.parse_game_detail_json`, a second embedded `var page = ["Game", {"game": {...}, "detail": {...}}]` script — `detail.appid` is the Steam AppID directly, `None` if the game has no Steam release) and its `deals` (`POST https://isthereanydeal.com/api/game/info/` with `{"gid": ...}`, same anonymous session-token auth as discovery — each deal's `url` is an `itad.link/...` redirect resolved to its real storefront URL before matching). `resolver.py` is this: `resolve_game` does the fetch+resolve for one slug, `resolve_game_with_aliases` additionally merges in ids from any slug reviewed in `config/isthereanydeal-game-aliases.yml` as the exact same game listed separately per platform (confirmed real: a Steam DLC and its Epic counterpart, `pinball-fx-my-little-pony-pinball`/`my-little-pony-pinball`, each got their own unrelated ITAD entry), and `resolve_isthereanydeal_markers` is what `search.complete_game_list` calls per game. Every game's `ids` also always gets `isthereanydeal:<slug>` itself (from the bundle parser, unconditionally) as a stable anchor for this follow-up, independent of which bundle it was first seen in.

7. **Scheduled scraping.** `.github/workflows/weekly-isthereanydeal-scrape.yml` runs `game-collections scrape isthereanydeal --tab=live` every Monday (plus manual `workflow_dispatch`), mirroring the Humble workflow's rolling-branch/PR pattern (`automation/isthereanydeal-weekly-scrape`) — no `--non-interactive` flag exists here since this source has no interactive resolver step to suppress. The per-game solver above is never part of this scheduled run — it's a manual `complete` follow-up.

Pipeline pieces:

- `models.py` — `ItadArchive`/`ItadTier`/`ItadItem`/`ItadPrice`/`ItadDates` (the normalized, resolved bundle shape), `ItadGameArchive` (the normalized per-game detail-page shape), and `ItadListSummary`/`ItadPageInfo`/`ItadCounts` (the strict, validated shape of one list-API entry).
- `provider_config.py` — `ItadProviderConfig`/`ItadProviderMapping`, `load_provider_config`, `resolve_provider_slug`, `slugify_provider_name`.
- `shop_config.py` — `ItadShopConfig`/`ItadShopEntry`, `load_shop_config` (the reviewed shop table, corroboration/reference-only).
- `game_alias_config.py` — `ItadGameAliasConfig`, `load_game_alias_config` (reviewed groups of ITAD slugs that are the same real game across platforms).
- `parser.py` — `parse_bootstrap_page`, `parse_list_page`, `parse_bundle_detail_json` (primary), `parse_bundle_detail_page` (BeautifulSoup-based fallback), `parse_game_detail_json` (the per-game detail page), `real_provider_url`/`real_provider_slug`.
- `resolver.py` — `parse_unresolved_marker`, `resolve_game`, `resolve_game_with_aliases`, `resolve_isthereanydeal_markers`, `write_itad_game_archive` (the per-game detail-page solver backing `complete --provider isthereanydeal`).
- `crawler.py` — `ItadHttpClient` (bounded-retry `httpx` wrapper; `bootstrap()`/`list_page(tab, offset)`/`fetch(url)`/`fetch_deals(gid)`/`resolve_redirect(url)`), `crawl_itad_offers(fetch, list_page, provider_config, tabs=("live",), shop_names=None, ...)` takes **two injectable callables** (`fetch` for plain GETs, `list_page` for the discovery API) rather than a client object, so tests never need real HTTP, plus the same `log`/`on_offer`/`archive_root` conventions as the other sources. Tries `parse_bundle_detail_json` first, falling back to `parse_bundle_detail_page` on `None`/a parse error. `write_itad_offer(...)` always writes `archives/isthereanydeal/bundle/<id>/{metadata.json,source.json}`, and — unless the dedup check above says otherwise — one `lists/<provider>/bundle/<date>_<slug>/<tier-id>.yml` per cumulative tier.

## Adding a new source (e.g. another bundle shop)

Use `humblebundle/` as the template for a source with resolver-based ID matching, or `dailyindiegame/` for one where the shop's own pages already give you a direct storefront ID. A new source is its own package `src/game_collections/sources/<source>/`, wired into the CLI the same way:

1. **Models** (`<source>/models.py`) — a strict Pydantic archive shape for the offer, analogous to `HumbleArchive`/`HumbleTier`/`HumbleItem` or the flatter `DigArchive`/`DigItem`. Base new models on `game_collections.models.StrictModel`/`NonEmptyString` so unknown fields and bad types fail loudly rather than silently rewriting bad data. Add a `schema_version: Literal[1] = Field(alias="schema", ...)` field so the archive is versioned like the existing sources.
2. **Parser** (`<source>/parser.py`) — turns the shop's raw page (embedded JSON, HTML, or an API response) into `(archive, source_payload)`, where `source_payload` is the relevant raw data worth preserving verbatim. Raise a source-specific parse error (mirror `HumbleParseError`/`DigParseError`) on anything unexpected instead of guessing. Don't assume page structure is fixed even within one site — DailyIndieGame's bundle title format alone has at least two variants; find a stable marker (a CSS class, a URL pattern) rather than matching exact wording.
3. **Resolver** (`<source>/resolver.py`, only if the shop's pages don't already give a direct storefront ID) — maps each product title to a qualified storefront ID (`steam:<appid>`, `gog:<id>`, etc). Reuse the existing storefront search machinery in `game_collections.search`/`StorefrontResolver`-style matching rather than reinventing per-store search. Persist reviewed decisions to a `config/<source>-store-ids.yml`-style resolution map (mirror `HumbleResolutionMap`/`render_resolution_map`) so re-crawling doesn't re-prompt for already-resolved titles, and record `unresolved:source:<source>:<key>` when nothing matches under `--non-interactive`. Skip this entirely if, like DailyIndieGame, the source page already links straight to a storefront ID.
4. **Crawler** (`<source>/crawler.py`) — a fetcher (mirror `HumbleHttpClient`'s bounded-retry `httpx` wrapper, or `DigBrowserClient`'s browser-based approach if the site needs one) plus a `crawl_*_offers(fetch, ..., archive_root=None, log=_NO_LOG, on_offer=None)` function that takes an **injectable `fetch` callable**, discovers or fetches explicit offers, and returns a report of successes and isolated per-offer errors (mirror `HumbleCrawlReport`/`DigCrawlReport`) so one bad page doesn't abort the whole run — and so tests never need a live network/browser. Log progress (`"Bundle x/y"`/`"Offer x/y"` and any per-item inner loop) via `log`, invoke `on_offer` as soon as each offer is ready, and skip expensive work via `sources.common.load_cached_archive` when `archive_root` is given and a valid cache entry exists (see "Progress logging, incremental writes, and resuming" above for the pattern to follow). A `write_*_offer(...)` function then atomically writes (reuse `sources.common.atomic_write`/`dump_json`/`render_game_list_yaml`) the normalized `archives/<source>/.../metadata.json` + `source.json`, and one `lists/<source>/...` YAML per purchasable tier/offer, each referencing its offer URL and archive files via `Reference`.

Then:
