# Sources

A "source" scrapes a public storefront/bundle page into launcher-neutral `lists/` entries plus a normalized `archives/` record, as opposed to `launchers/`, which synchronizes already-owned lists into a launcher library. `common.py` holds the file-writing helpers shared by every source (`atomic_write`, `dump_json`, `dump_versioned_json`, `render_game_list_yaml` — temp file + `fsync` + rename, deterministic sorted JSON, the version-envelope wrapper (see below), and the YAML list renderer with its IDE schema comment) plus `load_cached_archive`, the resume-from-disk helper all five sources use (see below), and `existing_list_match`/`backfill_existing_lists` — the dedup-and-cross-check pair shared by every bundle-*aggregator* source (isthereanydeal, dekudeals) that re-lists offers a dedicated scraper already covers (see isthereanydeal's dedup bullet below for how it's used). `storefronts.py` holds `StoreName`/`STORE_ROOTS`/`STORE_HOSTS`/`parse_store_identity`/`match_store`/`normalized_title`/`slugify_provider_name` — parsing a storefront URL (Steam/GOG/Epic/Ubisoft/Humble Store) into a qualified ID, comparing two titles, or falling back to a kebab-case provider slug — shared by any source that needs it, independent of whichever source package first needed it. It also holds `qualified_ids_from_urls`/`is_known_store_url`/`EXTRA_STORE_PARSERS` — a wider, ITAD-only extension for storefronts with no launcher-sync relevance (Microsoft Store, 2game, ...), each added only once a real deal redirect has confirmed its URL shape; an unmatched shop is skipped, never guessed. `names.py` holds `SourceName`, the one canonical enum of every crawler name (`humblebundle`/`greenmangaming`/`dailyindiegame`/`isthereanydeal`/`dekudeals`), reused wherever a source name is stored as data (e.g. `ScrapedTimestamp.source`) rather than re-typed as an ad-hoc string. Humble Bundle, DailyIndieGame, Green Man Gaming, isthereanydeal, and DekuDeals are the five implemented sources.

### Confidence-scored dates and the version envelope

Every archive's `dates.start`/`dates.end` (or ITAD's `expiry`) is a `ScrapedTimestamp | None` (`sources/timestamps.py`), not a bare `datetime`: `{iso, timestamp, confidence, source}`, since `start`/`end` are real page/API fields on some sources but missing, estimated, or timezone-unverified on others (Humble/ITAD/DekuDeals: confidence 1.0, a real field when present; Green Man Gaming's `end`: 0.7, real but an unverified-timezone index-page field; DailyIndieGame's `end`: 0.5, computed from a countdown timer relative to crawl time, not a fixed timestamp; both sources' `start`: `None`, no known source, never fabricated). `build_scraped_timestamp(value, source, confidence)` wraps an already-parsed, tz-aware `datetime`; `merge_scraped_timestamp(existing, fresh, ...)` decides whether a freshly-derived value should replace what's on disk — a `0.0`-confidence (legacy, pre-migration) value is always replaced, two agreeing 1.0 values keep whichever `iso` is more precise, and a real disagreement is resolved interactively on a TTY (prompted) or by keeping the chronologically older value non-interactively (`--git`/CI), always logged either way. `first_seen` (also on every `*Dates` model) is set once, the first time an archive is ever written for that key, and never overwritten afterward.

Every `metadata.json`/`source.json` is wrapped in a generic version envelope (`versioning.py`): `{"version": [year, month, day, hour, minute, second, fraction], "data": {...}}` (`Versioned[VERSION, DATA]`), replacing each source's old embedded `schema_version`/`schema`-aliased field entirely. `SchemaDateVersion` is the version type — a comparable `NamedTuple` (date-only, or date+hour+minute together, optionally +second, optionally +fraction — never a coarser field missing while a finer one is given) — hand-bumped as a `<SOURCE>_V<N>` constant in each source's `models.py` on every shape change; each source also declares a `Literal[...]` of every version it has ever had (`HumbleVersions`/`GmgVersions`/etc.) plus a single-value `Literal[<latest>]` (`HumbleCurrentVersion`/etc.) so "this object is definitely fully migrated" is a static type, not just a runtime check. `versioning.trajectory(initial_version, initial_data, steps)` lazily yields one `Versioned` snapshot per outstanding migration step for one file — never the whole end-to-end result in one call — so an outer wavefront driver can advance many files exactly one step at a time, grouping them by `(source, file_kind, version)` for a small number of clean commits (one per version-step group for content, batched ≤100 files with a counter for list-file renames) instead of either "one commit per file" or "the whole tree jumps versions at once." `load_cached_archive` peeks a file's `version` before validating `data` against the current model — a mismatch (including the sentinel `LEGACY_VERSION` for a pre-envelope flat file) is treated as a cache miss, since migrating a stale file to current is the wavefront's job, not something the cache-read path does itself. Every `scrape` command runs `cli._migrate_source_archives` first thing (via `migrations.schema_versions.discover_archive_paths`/`plan_migrations`/`apply_migration_group`), migrating that source's *entire* `archives/<source>/` tree to current before any fetch/resolve/write happens — committed as its own zero-or-more schema-migration commits when `--git` is set, ahead of the run's own single crawl-content commit. The single `game-collections migrate` command (`--type metadata`/`--type source`, `--path`/`--source` filters, `--apply`/`--git`, dry-run by default) drives the identical engine for migrating without crawling, e.g. to bring the whole repo's `archives/` up to date in one deliberate pass - the same command's `--type bundle` runs the analogous versioned migration for `lists/**/*.yml` bundle files instead (see `migrations/list_versions.py`); all three types run together when `--type` is omitted.

### Progress logging, incremental writes, and resuming

`crawl_humble_offers`/`crawl_dig_offers`/`crawl_gmg_offers`/`crawl_itad_offers`/`crawl_deku_offers` all accept:

- `log: Callable[[str], None]` — called with human-readable progress lines as the crawl runs ("Bundle x/y: ...", "Offer x/y: ...", "  Game x/y: ..."), so the CLI can print `typer.echo` output live instead of staying silent until the whole crawl finishes. Defaults to a no-op so existing calls/tests are unaffected.
- `on_offer: Callable[[CrawledOffer], None] | None` — called immediately once each offer/bundle finishes processing, so the CLI writes it to disk right away (`write_dig_offer`/`write_humble_offer`, plus `write_resolution_map` for Humble) instead of batching every write until the whole crawl completes. A crash or interrupt partway through only loses the in-flight offer, not everything already done.
- `archive_root: Path | None` — when given, enables resume-from-disk: before doing the expensive part of a target, `sources.common.load_cached_archive(ArchiveModel, metadata_path, source_path, current_version=CURRENT_VERSION)` is tried first. A hit (valid JSON, envelope `version` exactly `current_version`, and `data` still validates against the current model) skips the expensive work entirely and reuses the cached, already-processed result. A version bump makes old cache entries a miss automatically (see "Confidence-scored dates and the version envelope" above), so stale cache is never silently trusted — it just falls through to a real fetch (after the migration wavefront brings it up to date first, for a normal `scrape --git` run). Passing `archive_root=None` (what `--refresh`/`--no-cache` does on every `scrape` command) disables this and forces everything to be redone.

**Recovery of failed builds (Humble).** When building an offer's models fails (e.g. a pydantic `ValidationError` on a scraped field), its already-extracted payload is parked in `archives/humblebundle/recovery/<url-slug>.json` (`sources/recovery.py`) together with the error type, message and pydantic's structured `errors()` (field location and offending input). It is deliberately kept out of the real `choice/`/`bundle/` archive directories and is gitignored. The next run builds from that payload instead of fetching the page again, and deletes the file once the offer has been written to its real location. `--refresh` ignores and overwrites parked payloads. Other sources can adopt the same helper; their keys are known before the fetch.

The five sources skip different amounts of work on a cache hit, because of what's knowable before any fetch happens:

- **DailyIndieGame**: bundle numbers are known upfront (from the index page or explicit `--url`), so a cache hit skips the bundle-page fetch *and* every per-game listing-page fetch for that bundle — the biggest win, since each is a full headed-browser page load and most bundles in a discovery-mode run were already scraped last time (bundles roll off/on gradually, hence the overlap).
- **Humble Bundle**: the cache key depends on parsed fields, so the page itself is always fetched — but a cache hit skips `StorefrontResolver.resolve_archive`, which is the actually expensive part (one storefront search per distinct game).
- **Green Man Gaming**: bundle slugs are known upfront (from the index page or explicit `--url`), so a cache hit skips the bundle-page fetch, every per-item product-fragment fetch, *and* `StorefrontResolver.resolve_archive` — the same two expensive stages DailyIndieGame and Humble each separately skip, combined, since this source needs both a per-item enrichment fetch (DRM label, needed before resolution can pick a store) and title-based resolution.
- **isthereanydeal**: bundle ids are known upfront from the (always-fetched) discovery API, so a cache hit skips only the per-bundle detail-page fetch/parse — there's no separate resolution stage here since storefront IDs are read directly off the detail page, not searched for.
- **DekuDeals**: bundle slugs are known upfront (from the index page's embedded JSON or explicit `--url`), so a cache hit skips the bundle-page fetch *and* every per-item `/items/<slug>` page fetch — but even on a full (non-cached) crawl, an item slug already present in `config/dekudeals-store-ids.yml` (the persisted resolution map, populated as items get resolved) skips its own `/items/<slug>` fetch too, independent of the bundle-level archive cache, since the same game keeps recurring across many different bundles.

## Humble Bundle (`humblebundle/`)

Backs `game-collections scrape humblebundle`. Pipeline:

- `crawler.py` — `HumbleHttpClient` (small retrying `httpx` client for public HTML) and `crawl_humble_offers(...)`, which either fetches the explicit `--url` list or discovers the current Choice month (`CHOICE_URL`) and every active Games bundle from the bundle index (`BUNDLES_URL`); see "Progress logging, incremental writes, and resuming" above for its `log`/`on_offer`/`archive_root` parameters. `write_humble_offer(...)` then atomically writes (via `sources.common.atomic_write`) the normalized `archives/humblebundle/.../metadata.json` + `source.json`, and one merged `lists/humblebundle/...` YAML per bundle (`choice/YYYY-MM.yml`, or `bundle/<key>.yml`), recording every advertised cumulative tier in its `tiers`/`Game.tiers` fields (see `lists/README.md`) rather than one file per tier. An offer with no games at all (e.g. a software-only bundle) still gets its archives written, but no list, since a list needs at least one game.
- `parser.py` — extracts the embedded JSON payload from Humble's page HTML (`parse_choice_page`, `parse_bundle_page`, `parse_bundle_index`) into a `HumbleArchive` plus the raw source payload; converts descriptions to Markdown.
- `resolver.py` — `StorefrontResolver` matches each Humble product title against real storefronts (Steam, GOG, Epic, Ubisoft, Humble Store) via `STORE_SEARCH_URLS`. Unique exact matches resolve automatically; ambiguous matches prompt for a candidate or canonical URL/ID (or record `unresolved:source:humblebundle:<machine-name>` under `--non-interactive`). Reviewed decisions persist in `config/humblebundle-store-ids.yml` (a `HumbleResolutionMap`) so re-running the scraper doesn't re-prompt for already-resolved titles. A pasted value that is not a valid store URL/ID is rejected and asked for again rather than failing the whole offer. For `dlc`-badged items, every top-level `<ul>` of the description is a separate candidate list (`HumbleItem.dlc_lists`), decided one list at a time by `dlc_lists.classify_dlc_list`: bullets that read as prose (` — ` separators, long sentences) are explainer text ("no", no prompt); a Steam base-game link plus an exact Steam match for the first bullet is "yes" (the items become split games requiring the base game); anything else is asked ("Are these separate games/DLCs?") and the answer is cached under `dlc_lists` in the resolution map as `<machine-name>::list<N>`. Once a list is confirmed, later undecidable lists of the same item are treated as explainer text. Under `--non-interactive` an unsure list is always "no". `resolve_archive(...)` also takes a `log` callback, called once per distinct game it resolves ("  Game x/y: ...") — the only place that knows the per-game count during resolution. For the `steam` provider specifically, `_search_steam` tries `store.steampowered.com` first (cheap, no browser) and only falls back to `steamdb.info`'s own app search — often better at finding the exact product for a noisy Humble title — when steampowered.com doesn't already give a unique exact-title match. steamdb.info sits behind a Cloudflare *managed* (Turnstile-class) challenge, confirmed live to defeat plain `httpx`/`curl`, TLS-fingerprint impersonation (`curl_cffi`), and JS-VM challenge solvers (`cloudscraper`, in both its PyPI release and a third-party fork) alike — only a real headed browser session passes it, same situation as `dailyindiegame`'s Cloudflare challenge below. `steamdb.py`'s `SteamDbBrowserClient` (a `patchright` headed persistent context, mirroring `dailyindiegame.crawler.DigBrowserClient`) is only launched lazily on the CLI's first actual fallback use (see `cli._LazySteamDbFetcher`), so a run where steampowered.com resolves everything never pays the browser-launch cost; if the browser can't launch at all (missing `patchright`, headless CI runner, ...), the CLI logs a warning and every later `steam` lookup just falls back to steampowered.com-only for the rest of the run.
- `models.py` — `HumbleArchive`/`HumbleItem`/`HumbleResolution`: the strict Pydantic shape of the normalized archive, validated against `schemas/humblebundle-archive.schema.json`.

`scripts/backfill_humble_choice.py` is a standalone script (not part of this package) that reuses these same crawler internals (plus `sources.common`) to backfill historical Choice months from a third-party mirror, since Humble's own site only exposes the current month to guests.

### Scheduled scraping

`.github/workflows/weekly-humblebundle-scrape.yml` runs `game-collections scrape humblebundle --non-interactive` every Monday (plus manual `workflow_dispatch`) and opens/updates a pull request with any new offers. It reuses a single rolling branch (`automation/humblebundle-weekly-scrape`) across weeks — rebasing it onto `main` if it survived from last week's still-open PR, or recreating it from `main` if last week's PR was merged/closed — and never fails the job on unresolved storefront IDs, since those are an expected, committable state for later manual `game-collections complete` follow-up.

## DailyIndieGame (`dailyindiegame/`)

Backs `game-collections scrape dailyindiegame`. This source differs from Humble in three ways worth knowing before touching it:

1. **The site sits behind a Cloudflare managed challenge.** Plain `httpx`/`curl` get an instant 403. Worse, a stock **headless** Playwright/Chromium session (even the `patchright` fork built specifically to evade bot detection) hangs on the challenge page forever — Cloudflare fingerprints CDP-driven headless automation and never resolves it. Only a **headed** `patchright` persistent context (`headless=False`, a real, non-headless Chromium) actually passes the challenge; this was confirmed against the live site, not assumed. `DigBrowserClient` in `crawler.py` implements this: `sources/browser.py`'s `launch_background_context` (`chromium.launch_persistent_context(user_data_dir, headless=False, no_viewport=True, args=["--start-minimized"])`, so the window starts minimized and one tab is reused for every fetch instead of opening a new, window-activating tab each time), then polls the tab title (skipping past `"Just a moment..."` and the post-challenge `"Loading ..."` redirect) rather than trusting `wait_until="networkidle"` — this site's persistent connections mean network never truly idles, so a bounded `wait_for_load_state("networkidle", ...)` is used as a best-effort settle step only, always followed by a fixed extra wait. A GitHub Actions runner (or any other unattended/headless-only environment) may not be able to run this at all — there is currently no scheduled workflow for this source (unlike Humble's) for exactly this reason.
2. **No resolver needed.** Every game on a bundle page links directly to `https://store.steampowered.com/app/<id>` — the Steam AppID is already given in the page, so there's no title search/matching/resolution-map/`unresolved:*` machinery like Humble's `StorefrontResolver`. This source only ever produces `steam:<id>` IDs.
3. **No structured dates or fixed bundle-name format.** There's no embedded JSON or `<time>`/meta date anywhere; the only signal is a live countdown string (`"Bundle ends in D days : HH : MM : SS"`), parsed relative to the crawl timestamp. The bundle's display name isn't one fixed literal either — it varies by promotion (`"DIG Bundle <N> - ADULT"`, `"FRIDAY BARGAIN <N>"`, and presumably others not yet seen) — so the parser reads it from the first `<span class="DIG-contentOrangeBIG">` on the page (a stable marker across naming schemes) rather than matching a specific prefix, and derives `is_adult` from whether that text contains `"ADULT"`.

Pipeline pieces:

- Bundles still linked from the index after they expired only show "This bundle has ended." (confirmed live, e.g. `site_weeklybundle_2420.html`); `parse_bundle_page` raises `DigBundleEndedError` for them and `crawl_dig_offers` logs a skip instead of recording an error.
- `models.py` — `DigArchive`/`DigItem`/`DigPrice`/`DigDates`: flatter than Humble's shape since there's one flat price tier per bundle (not cumulative tiers) and no resolver-produced fields.
- `parser.py` — `parse_bundle_index_page` (weekly-bundle numbers from the `site_content_bundles.html` gallery), `parse_bundle_page` (title span, price-summary sentence, countdown, per-game Steam links via a small `<td>`-tracking `HTMLParser`), `parse_game_listing_page` (each game's own `site_gamelisting_<id>.html` for price/region/description/cover art).
- `crawler.py` — `DigBrowserClient` (see above), `crawl_dig_offers(fetch, ...)` takes an **injectable `fetch` callable** exactly like Humble's crawler (plus `log`/`on_offer`/`archive_root`, see above), so every test exercises real parsing/orchestration logic with a fake `fetch` and never launches a browser; only the CLI wires in the real `DigBrowserClient.fetch`. `write_dig_offer(...)` writes `archives/dailyindiegame/bundle/<N>/{metadata.json,source.json}` and `lists/dailyindiegame/bundle/<N>.yml`.

## Green Man Gaming (`greenmangaming/`)

Backs `game-collections scrape greenmangaming`. Notable differences from the other two sources:

1. **Two domains, both plain server-rendered HTML.** The bundle index lives at `greenmangaming.com/bundles/` (an Angular app, but the bundle grid itself is rendered server-side into a `<div class="product-grid">`, not fetched via an API call); each bundle's own pages live on a *different* domain, `greenmangamingbundles.com` (a separate Django + htmx app). Neither needs a browser or hits a bot challenge — plain `httpx` GETs work for everything, including the htmx product-detail fragment (fetched with an `HX-Request: true` header, same as the real frontend would send).
2. **Resolver-based ID matching, like Humble.** Bundle pages never link straight to a storefront ID — only a free-text DRM label per item (`<dt>DRM</dt><dd>Steam</dd>`, fetched from that item's own `/bundles/<slug>/product/<id>/` fragment). `resolver.py` mirrors `humblebundle/resolver.py`'s `StorefrontResolver`/store-search machinery (re-exported from it, not reimplemented) with a `redeem_on_for_drm` mapping (`Steam`→`steam`, `GOG`→`gog`, `Uplay`/`Ubisoft Connect`→`ubisoft`; anything unrecognized is left unresolved rather than guessed).
3. **Cumulative tiers derived from the default page render, no extra requests.** A bundle detail page's default render shows every item across every tier "unlocked" at once, and each item's `hx-vals` attribute (used by the site's own tier-switching htmx interaction) already tags it with the *tier it was originally unlocked at* (`tier_name`). `parser.py` groups items by that tag and accumulates them in ascending tier-price order to build each cumulative tier — this was cross-checked against the live site's `/bundles/<slug>/switch_tier/` endpoint (which returns exactly the same cumulative sets per tier) before trusting it, so no extra per-tier fetch is needed, unlike DailyIndieGame's per-game listing-page fetches.

Pipeline pieces:

- `models.py` — `GmgArchive`/`GmgTier`/`GmgItem`/`GmgPrice`/`GmgResolution`: cumulative tiers like `HumbleArchive`/`HumbleTier`, but flatter items (no `is_game`/bonus distinction — every item observed in a GMG bundle is a purchasable product, DLC included).
- `resolver.py` — `StorefrontResolver`/`GmgResolutionMap`/`redeem_on_for_drm`, importing `STORE_ROOTS`/`StoreName`/`parse_store_identity`/`normalized_title` from `sources.storefronts` and `STORE_SEARCH_URLS`/`StoreCandidate`/`parse_store_candidates` from Humble's resolver instead of duplicating them. Reviewed decisions persist in `config/greenmangaming-store-ids.yml`. Mirrors Humble's steampowered.com-first, steamdb.info-fallback `_search_steam` behavior for the `steam` provider too (see Humble Bundle's resolver section above), importing the shared `STEAMDB_SEARCH_URL`/`parse_steamdb_results`/`SteamDbBrowserClient` pieces from `humblebundle.steamdb`.
- `parser.py` — `parse_bundle_index_page` (video-games-category bundle slugs from the index page's `product-card`/`cta-button` markup), `parse_bundle_page` (title, currency, and cumulative tiers per the tier-grouping approach above), `parse_product_fragment` (DRM/platform/developer/publisher/description from one item's htmx fragment).
- `crawler.py` — `GmgHttpClient` (bounded-retry `httpx` wrapper, sends `HX-Request: true` so product-fragment fetches work), `crawl_gmg_offers(fetch, resolver, mapping, ...)` takes the same **injectable `fetch` callable** plus `log`/`on_offer`/`archive_root` conventions as the other sources. `write_gmg_offer(...)` writes `archives/greenmangaming/bundle/<slug>/{metadata.json,source.json}` and one merged `lists/greenmangaming/bundle/<slug>.yml`, with every cumulative tier recorded in its `tiers`/`Game.tiers` fields.

## isthereanydeal (`isthereanydeal/`)

Backs `game-collections scrape isthereanydeal`. This source is structurally different from the other three: it's a bundle *aggregator*, not a bundle seller, so it discovers bundles hosted on many different platforms and writes into each one's own `lists/<provider>/` directory rather than a single `lists/isthereanydeal/` tree — `archives/isthereanydeal/...` is the only thing that's always this source's own.

1. **Discovery needs a plain anonymous bootstrap, not a resolver.** `GET https://isthereanydeal.com/bundles/` sets a `sess2` session cookie and embeds a matching CSRF-style token plus a shop-id→name table in an inline `var g = {...}` script (`parser.parse_bootstrap_page`). That token is then sent as the `itad-sessiontoken` header on `POST /bundles/api/list/?tab={live,expired,pending}` (`{"offset": N, "sort": null, "filter": null}`, paginated by 30 until `"done": true`) — a request missing the header, or one whose `Accept` isn't `application/json`, gets routed to the HTML fallback page or a `400`. None of this involves any real account; it's the same anonymous bootstrap any visitor's browser performs.
2. **The list API's own embedded tier/game preview is deliberately not modeled.** Each summary entry also carries a `tiers` array with ITAD-internal game ids/slugs/asset URLs/shop-key numbers — a higher-churn duplicate of what the bundle's own detail page gives with real storefront IDs, and unused here. `parser.parse_list_page` strips it (`_without_tiers_preview`) before validating the rest through `ItadListSummary`, so the archive's `source.json` stays strict (fails loudly on any *other* unexpected field) without being brittle against that specific blob's asset/platform/type enum churn.
3. **Tiers and per-game storefront IDs come from the detail page's own embedded JSON, not DOM scraping.** Every `GET https://isthereanydeal.com/bundles/<id>/` (server-rendered HTML) carries a shared inline `<script>` declaring both `var g = {...}` (token/shops config) and `var page = ["Bundle", {"liveData": {"tiers": [...]}}];` (this page's own SSR'd state) — confirmed live, the same script tag on every page. `parser.parse_bundle_detail_json` is the primary parser: `liveData.tiers` is a list of **per-tier-exclusive** (not cumulative) `{"price": [cents, "CUR"] | null, "note": ..., "games": [...]}` entries, so it accumulates each tier's `games` onto a running cumulative list to reproduce `ItadTier.items`'s expected cumulative shape (confirmed against a live 3-tier GreenManGaming-hosted bundle: 2/2/2 exclusive games per tier summed to its known 6-game total). Tier display names come from `tier.note` when the provider sets one (confirmed `"Bronze"/"Silver"/"Gold"` for GreenManGaming), falling back to the dedicated Humble scraper's own `entire-{n}-item-bundle`/`{n}-item-bundle` convention for Humble-provider bundles (which never carry a `note`), or a generic `Tier N` otherwise. Each game's storefront IDs come from its `reviews[].url` entries (`{"source": "Steam", "url": "https://store.steampowered.com/app/<id>/"}`) via the shared `sources.storefronts.parse_store_identity` — no resolver/title-search needed, and this works identically for mature-rated bundles (confirmed live: the mature-content gate only hides the page's *rendering*, not this embedded data). Not every game has a recognized link (confirmed live: some IndieGala/Fanatical bundles leave several games with no direct storefront link at all); those get `unresolved:source:isthereanydeal:<bundle-id>:<game-slug>`. `parser.parse_bundle_detail_page` is a DOM-based fallback (BeautifulSoup, not regex) covering the rare case where the embedded JSON is missing or malformed — `crawler.crawl_itad_offers` tries the JSON path first and only falls back to it (logging a note) on `None`/a parse failure; kept intentionally rather than removed, as a hedge against ITAD ever dropping that script.
4. **A reviewed shop table corroborates resolved ids, never resolves them by itself.** `config/isthereanydeal-shops.yml` (`shop_config.load_shop_config`, `schema: 2`) lists every ITAD shop as `{name, id, slug}` — `id` mirrors the bootstrap script's shop-id table (`61: Steam`, `35: GOG`, etc; two entries, App Store/Google Play, have no ITAD shop id at all), `slug` is the qualified-id prefix once that shop's storefront URL shape has been verified (see `sources.storefronts`). Each game's `keys` (shop-id ints) are compared against the provider(s) its `reviews[].url` actually resolved to, purely to log a one-line mismatch warning — resolution itself is always URL-based, via `sources.storefronts.qualified_ids_from_urls`, which recognizes more than just the original 5 launcher stores (Microsoft Store, 2game, ...); an unverified shop's deal/review link is simply skipped, not guessed.
5. **Provider-slug resolution and dedup, not a resolution map.** `page.name` (the aggregator's label for the bundle's origin platform, e.g. `"GreenManGaming"`, `"Fanatical"`) maps to our `lists/<provider>/` directory name via a small reviewed `config/isthereanydeal-providers.yml` (`provider_config.resolve_provider_slug`; an unreviewed provider falls back to a slugified name with a logged warning instead of failing). The bundle's real, provider-native slug is decoded from its affiliate-redirect `url` field (`parser.real_provider_slug` — handles the `u=`/`ued=` wrapper conventions seen so far, or the unwrapped URL directly for providers like IndieGala that don't redirect at all). Before writing `lists/<provider>/...`, `crawler.write_itad_offer` matches that slug against every existing path under `lists/<provider>/` via `sources.common.existing_list_match` — an exact substring match (Humble's own directories are date-prefixed, hence substring rather than exact) is trusted immediately, and failing that, a fuzzy name match (e.g. a slug differing only by a stopword) is only accepted once the candidate's own game roster actually overlaps the ITAD-derived one, confirmed interactively on a TTY or only auto-accepted non-interactively above a stricter threshold — the archive record is always written regardless. A match doesn't mean permanent silence, though: every `GameList` (public models, `../../models.py`) carries a `crawlers` field naming which crawler module(s) have contributed to or verified it. If the matched list(s) don't yet list `isthereanydeal`, `crawler._backfill_existing_lists` does a one-time cross-check instead of skipping — matching each existing game by name against the ITAD-derived roster (`sources.common.find_matching_game`) and adding any qualified ID whose *provider* the existing game doesn't already carry (never overriding or duplicating a provider the dedicated scraper already resolved), merging in ITAD's own reference and `crawlers` entry (`sources.common.merge_references`/`merge_crawlers`). Only once every matched list already lists `isthereanydeal` does a later run go back to a quiet no-op skip.
6. **The per-game detail-page solver is a separate, on-demand follow-up, not part of the crawl.** Games with no recognized storefront link on the bundle detail page get `unresolved:source:isthereanydeal:<bundle-id>:<game-slug>`; `game-collections complete FILE --provider isthereanydeal --mode unresolved` resolves these later by fetching that game's own `https://isthereanydeal.com/game/<slug>/info/` page (`parser.parse_game_detail_json`, a second embedded `var page = ["Game", {"game": {...}, "detail": {...}}]` script — `detail.appid` is the Steam AppID directly, `None` if the game has no Steam release) and its `deals` (`POST https://isthereanydeal.com/api/game/info/` with `{"gid": ...}`, same anonymous session-token auth as discovery — each deal's `url` is an `itad.link/...` redirect resolved to its real storefront URL before matching). `resolver.py` is this: `resolve_game` does the fetch+resolve for one slug, `resolve_game_with_aliases` additionally merges in ids from any slug reviewed in `config/isthereanydeal-game-aliases.yml` as the exact same game listed separately per platform (confirmed real: a Steam DLC and its Epic counterpart, `pinball-fx-my-little-pony-pinball`/`my-little-pony-pinball`, each got their own unrelated ITAD entry), and `resolve_isthereanydeal_markers` is what `search.complete_game_list` calls per game. Every game's `ids` also always gets `isthereanydeal:<slug>` itself (from the bundle parser, unconditionally) as a stable anchor for this follow-up, independent of which bundle it was first seen in. A slug can also turn out to be a "collection" packaging several separately-sold games with no storefront release of its own (`appid: null`, no `deals`) - confirmed live for GreenManGaming's "WB Games: Blood & Grit Collection" bundle's own "FEAR Collection" entry, whose `games.packageContents` (from the same `api/game/info/` response) lists six real Steam games including a DLC/base-game pair ("FEAR 2: Reborn"/"F.E.A.R. 2 Project Origin", linked via that response's `games.dlcParents`). `resolve_game` resolves each constituent slug recursively (guarded against a slug re-appearing in its own package) into `splits`, `package_split_games` turns those into launcher-neutral `ResolvedGame`s (DLC `requires` included), and `resolve_isthereanydeal_markers`/`search.complete_game_list` explode that one draft game into one `Game` per constituent - the same `group`-linked split shape as a title-search "Multiple..." choice (`humblebundle.resolver.ResolvedGame`, reused here rather than duplicated) - instead of writing one unusable `isthereanydeal:fear-collection`-only id. `write_itad_game_archive` recurses into `splits` so every constituent gets its own `archives/isthereanydeal/game/<slug>/` archive too.

7. **Scheduled scraping.** `.github/workflows/weekly-isthereanydeal-scrape.yml` runs `game-collections scrape isthereanydeal --tab=live` every Monday (plus manual `workflow_dispatch`), mirroring the Humble workflow's rolling-branch/PR pattern (`automation/isthereanydeal-weekly-scrape`) — no `--non-interactive` flag exists here since this source has no interactive resolver step to suppress. The per-game solver above is never part of this scheduled run — it's a manual `complete` follow-up.

Pipeline pieces:

- `models.py` — `ItadArchive`/`ItadTier`/`ItadItem`/`ItadPrice`/`ItadDates` (the normalized, resolved bundle shape), `ItadGameArchive` (the normalized per-game detail-page shape), and `ItadListSummary`/`ItadPageInfo`/`ItadCounts` (the strict, validated shape of one list-API entry).
- `provider_config.py` — `ItadProviderConfig`/`ItadProviderMapping`, `load_provider_config`, `resolve_provider_slug`, `slugify_provider_name`.
- `shop_config.py` — `ItadShopConfig`/`ItadShopEntry`, `load_shop_config` (the reviewed shop table, corroboration/reference-only).
- `game_alias_config.py` — `ItadGameAliasConfig`, `load_game_alias_config` (reviewed groups of ITAD slugs that are the same real game across platforms).
- `parser.py` — `parse_bootstrap_page`, `parse_list_page`, `parse_bundle_detail_json` (primary), `parse_bundle_detail_page` (BeautifulSoup-based fallback), `parse_game_detail_json` (the per-game detail page), `real_provider_url`/`real_provider_slug`.
- `resolver.py` — `parse_unresolved_marker`, `resolve_game`, `resolve_game_with_aliases`, `resolve_isthereanydeal_markers`, `write_itad_game_archive` (the per-game detail-page solver backing `complete --provider isthereanydeal`).
- `crawler.py` — `ItadHttpClient` (bounded-retry `httpx` wrapper; `bootstrap()`/`list_page(tab, offset)`/`fetch(url)`/`fetch_deals(gid)`/`resolve_redirect(url)`), `crawl_itad_offers(fetch, list_page, provider_config, tabs=("live",), shop_names=None, ...)` takes **two injectable callables** (`fetch` for plain GETs, `list_page` for the discovery API) rather than a client object, so tests never need real HTTP, plus the same `log`/`on_offer`/`archive_root` conventions as the other sources. Tries `parse_bundle_detail_json` first, falling back to `parse_bundle_detail_page` on `None`/a parse error. `write_itad_offer(...)` always writes `archives/isthereanydeal/bundle/<id>/{metadata.json,source.json}`, and — unless the dedup check above says otherwise — one merged `lists/<provider>/bundle/<date>_<slug>.yml`, with every cumulative tier (or, for a build-your-own-bundle offer, every pick-count variation) recorded in its `tiers`/`Game.tiers` fields.

## DekuDeals (`dekudeals/`)

Backs `game-collections scrape dekudeals`. Like isthereanydeal, this is a bundle *aggregator*: it re-lists offers actually sold by many other sites (Humble, Fanatical, itch.io, IndieGala, ...), so it writes into each bundle's own `lists/<provider>/` directory, not a single `lists/dekudeals/` tree — `archives/dekudeals/...` is the only thing that's always this source's own.

1. **Pages are Inertia.js views — the props are embedded JSON, not scraped markup.** Both the bundles index (`GET https://www.dekudeals.com/bundles`) and every bundle detail page (`GET https://www.dekudeals.com/bundles/<slug>`) embed their full server-rendered props as one HTML-entity-encoded JSON object in `<div id="inertia-app" data-page="...">`. `parser._inertia_props` finds the attribute's true end by scanning for the first raw `">` after it (the JSON itself has no literal `"`, only `&quot;`), then `html.unescape` + `json.loads`s it — confirmed live, far more robust than parsing the rendered bundle cards/tier tables by hand. `parse_bundle_index_page` reads `props.bundles[]` into `DekuIndexEntry(slug, created_at)` — `created_at` is the only place DekuDeals reports anything resembling a bundle's start date (the detail page itself never does), so the crawler carries it into `DekuDates.start` for bundles reached via discovery; an explicit `--url` crawl has no index summary to read it from, so `start` stays `None` there and the list filename's date prefix falls back to the crawl date instead (see point 5 below — don't assume "today" always means the crawl date). `parse_bundle_page` reads `props.bundle` (name, `store_name`, `tiering_style`, `ends_at`, the real affiliate `url`), `props.tiers` (price/`item_minimum` per tier), and `props.items` (name, slug, and which tier ids each belongs to).
2. **Three real `tiering_style` values, all modeled by one `DekuTier`.** `price_per_tier` (e.g. a Humble-hosted bundle: fixed cumulative price breakpoints, each item's own `tiers` list says which breakpoints unlock it) and `price_per_item` (a Fanatical-style Build Your Own bundle: every tier instead fixes an `item_minimum` pick-count over one shared pool at a given per-item price, and every item's `tiers` is empty since the whole pool is available at every count). `write_deku_offer` turns the first into ordinary cumulative `tiers`/`Game.tiers` (mirroring Humble/GreenManGaming), and the second into `pick_quota` tiers via the shared `sources.common.merge_tiered_games`, mirroring isthereanydeal's own BYOB handling. The third, `all_one_price` (confirmed live on e.g. `nuntius-games-bundle`: one flat price for the whole set), has a single tier listing every item and is written exactly like a one-tier `price_per_tier` bundle.
3. **Every item routes through DekuDeals' own `/items/<slug>` page, resolved immediately.** Unlike isthereanydeal (which gets a real storefront URL straight off the bundle's own detail page), a DekuDeals bundle only ever links to its own `/items/<slug>?platform=all` page. `crawler.crawl_deku_offers` fetches that page for every distinct item slug seen in a bundle (once per slug, even if the item recurs across several tiers) and `parser.parse_item_page` extracts every storefront URL from its `data-out-analytics-id='...' href='...'` anchor rows (a store-link row repeats the same `href` across three tag variants, deduped by that shared analytics id) — then `sources.storefronts.qualified_ids_from_urls` resolves whichever of those URLs it recognizes (in practice: Steam almost always, GOG/Epic/Ubisoft/Humble Store occasionally; Nintendo eShop/PlayStation Store/Xbox/Amazon links are silently skipped, not guessed, since there's no verified qualified-id shape for them yet). Every item's `ids` always also gets `dekudeals:<slug>` itself, unconditionally. An item page with no store links at all (e.g. a "goodies pack" of artwork) is therefore not an error, it just yields only that `dekudeals:<slug>` id; and a bundle item that has a name but no slug (e.g. the `RAT PACK random key` entry on `garbage-dwellers`) has no item page to resolve, so it is skipped and stays only in the raw `source.json`.
4. **Resolved item ids are cached in a persisted resolution map, not re-fetched per bundle.** `config/dekudeals-store-ids.yml` (a `DekuResolutionMap`, `resolver.py`) maps each item slug to its resolved ids once and for all — the same real game recurs across many different bundles over time, so `crawler._resolve_item_ids` checks this map before ever fetching `/items/<slug>` again. Unlike Humble/GreenManGaming's resolution maps, there's no interactive/`unresolved:*` step here: resolution is fully automatic (a store link is either recognized or silently dropped), so the map is a pure fetch-avoidance cache, not a reviewed decision log.
5. **Provider-slug resolution and dedup/backfill, mirroring isthereanydeal.** `bundle.store_name` (e.g. `"Humble"`, `"Fanatical"`) maps to our `lists/<provider>/` directory name via a small reviewed `config/dekudeals-providers.yml` (`provider_config.resolve_provider_slug`; an unreviewed store name falls back to `sources.storefronts.slugify_provider_name` with a logged warning). `write_deku_offer` then calls the same shared `sources.common.existing_list_match`/`backfill_existing_lists` isthereanydeal uses: a match against an existing `lists/<provider>/...` path skips writing a duplicate list, backfilling any storefront id DekuDeals resolved that the existing game doesn't already carry and recording `dekudeals` in that list's `crawlers` field, until every matched list already lists it.

Pipeline pieces:

- `models.py` — `DekuArchive`/`DekuTier`/`DekuItem`/`DekuPrice`/`DekuDates` (the normalized, resolved bundle shape).
- `parser.py` — `parse_bundle_index_page`, `parse_bundle_page` (returns a `DekuBundleDraft`/`DekuTierDraft`/`DekuItemDraft` — pre-id-resolution, since that happens in the crawler, not the parser), `parse_item_page`, `bundle_slug`.
- `provider_config.py` — `DekuProviderConfig`, `load_provider_config`, `resolve_provider_slug` (mirrors isthereanydeal's own, keyed by `store_name` string instead of a numeric provider id).
- `resolver.py` — `DekuResolutionMap`, `load_resolution_map`, `render_resolution_map`, `write_resolution_map` (mirrors Green Man Gaming's resolution-map persistence, minus the interactive/`unresolved:*` parts).
- `crawler.py` — `DekuHttpClient` (bounded-retry `httpx` wrapper), `crawl_deku_offers(fetch, provider_config, mapping, ...)` takes the same **injectable `fetch` callable** plus `log`/`on_offer`/`archive_root` conventions as the other sources, mutating `mapping.games` in place as new items get resolved. `write_deku_offer(...)` always writes `archives/dekudeals/bundle/<slug>/{metadata.json,source.json}`, and — unless the dedup check above says otherwise — one `lists/<provider>/bundle/<date>_<slug>.yml`, date-prefixed like every other source's bundle lists; since DekuDeals never reports a bundle's actual start date, the date it was first crawled (stable across cache hits, since it's read off the archive itself) stands in for it, mirroring isthereanydeal's own fallback.

## Fanatical (`fanatical/`)

Backs `game-collections scrape fanatical`. Fanatical sells the bundles itself, so unlike the aggregators this source owns `lists/fanatical/bundle/<YYYY-MM-DD>_<slug>.yml` and `archives/fanatical/bundle/<slug>/{metadata,source}.json`.

1. **One JSON endpoint, no HTML.** fanatical.com is a client-rendered SPA whose pages carry no bundle data. The page `/en/bundle/games` is fed by `GET https://www.fanatical.com/api/algolia/bundles` (confirmed live: plain JSON array, no authentication, only a browser-like `User-Agent`; the WAF blocks bare library defaults). It lists every currently listed `bundle` and `pick-and-mix` (Build-Your-Own) with tiers, per-currency prices, products and unix `available_valid_from`/`available_valid_until`. There is no per-bundle detail endpoint (`/api/{product,bundle,bundles}/<slug>` return 404, `/api/products/<slug>` a 403), so `--url` just selects slugs out of that same list and a bundle which is no longer listed is an error. `parser.parse_bundles_json` keeps the raw items verbatim (they become `source.json`), `parser.parse_bundle` validates one into a `FanaticalDraft` and raises `FanaticalParseError` on any shape change.
2. **Two tier shapes, one archive model.** A regular `bundle` lists only the *newly unlocked* products per tier (a comic bundle: 4 / 21 / 38 new products for 4 / 25 / 63 total), so `crawler._build_archive` accumulates them into cumulative `FanaticalTier.items`. A `pick-and-mix` lists its whole pick pool on the first tier alone (`products: null` on the rest) and each tier's `displayTotal` is the number of picks, so every archived tier shares the pool and `display_total` is the pick count. `write_fanatical_offer` turns the first into ordinary `tiers`/`Game.tiers` named after the USD price, the second into `pick N` tiers with a `pick_quota` through the shared `sources.common.merge_tiered_games` (a single purchasable pick count becomes a plain list-level `pick_quota`).
3. **Dates are exact.** `start`/`end` come straight from Fanatical's own unix timestamps (confidence 1.0); `first_seen` is set when a bundle is first archived.
4. **Storefront ids: Fanatical's `steamId`, then a Steam title search, then an `unresolved` marker.** Each product carries `steamId`/`steamIdType`, but only for some: an integer is trusted, `""`/`null` is unknown (confirmed live for roughly one in six games, plus every nested `type: "bundle"` edition inside a pick-and-mix). `resolver.resolve_product_ids` then searches the Steam store (`humblebundle.resolver.STORE_SEARCH_URLS` + `parse_store_candidates`) and only accepts a *unique exact* normalized-title match, never guessing between candidates; successes are cached in `config/fanatical-store-ids.yml` (`FanaticalResolutionMap`, product slug to ids) so a game recurring across bundles is searched once. Anything else gets `unresolved:source:fanatical:<bundle>:<slug>` for `game-collections complete`. Every item additionally carries `fanatical:<slug>` as a stable anchor. Books, comics and audio, and products not delivered via Steam, never search and only get the anchor.
5. **What becomes a list.** Only `game` and `bundle` (nested edition) products are written to a list, plus `software` which resolved to a Steam id (Fanatical's e-learning courses and asset packs are not on Steam). A bundle without any such product (all the book and comic collections) is archived but gets no list.
6. **Dedup against the aggregators.** isthereanydeal and dekudeals already wrote `lists/fanatical/...` for many of these bundles. `write_fanatical_offer` runs the shared `sources.common.existing_list_match`/`backfill_existing_lists`, but only trusts a match whose name is exactly this bundle's slug (`crawler.is_same_bundle`): the shared match is a substring match, which would otherwise treat `all-stars-bundle-2` or `fall-bundle-2023` (older editions) as covering today's `all-stars-bundle`/`fall-bundle` and backfill the wrong list. An exact match is backfilled with the `steam:` and `fanatical:` ids it lacks and gets `fanatical` recorded in `crawlers`; otherwise a new list is written.

Pipeline pieces:

- `models.py` - `FanaticalArchive`/`FanaticalTier`/`FanaticalItem`/`FanaticalDates`.
- `parser.py` - `parse_bundles_json`, `parse_bundle`, `bundle_slug`, `page_url`.
- `resolver.py` - `FanaticalResolutionMap` (load/render/write like the other maps), `steam_title_search`, `resolve_product_ids`.
- `crawler.py` - `FanaticalHttpClient` (bounded-retry `httpx` wrapper, also used for the Steam search), `crawl_fanatical_offers(fetch, mapping, search, ...)` with the usual injectable `fetch`/`log`/`on_offer`/`archive_root` conventions, and `write_fanatical_offer`.
- `migrations.py` - empty version-step lists (`FANATICAL_V1` is the first shape).

## Digiphile (`digiphile/`)

Backs `game-collections scrape digiphile`. Digiphile sells the bundles itself, so this source owns `lists/digiphile/bundle/<YYYY-MM-DD>_<slug>.yml` and `archives/digiphile/bundle/<slug>/{metadata,source}.json`, while dekudeals and isthereanydeal also mirror its bundles there.

1. **Server-rendered Next.js, no browser.** digiphile.co embeds its data in the page as React Server Component flight chunks (`<script>self.__next_f.push([1,"..."])</script>`); concatenating their string fragments yields plain JSON (confirmed live; plain `httpx` works, no Cloudflare challenge). `parser.flight_text` does that and `parser.extract_bundle_slugs` / `extract_bundle` read `"bundles":[...]` from `/collections` and `"bundle":{...}` from `/collections/<slug>`. The list only carries summaries, so every bundle needs its detail page, whose raw bundle object becomes `source.json` verbatim. The list has no pagination, includes expired bundles (back to 2025-11) and reports `status: "Active"` for all of them, so the dates are the truth. An unknown slug answers HTTP 200 with a Next.js 404 page, so a missing payload, not the status code, means the bundle is gone.
2. **Three tier types.** `Base` tiers are cumulative price breakpoints, each product points at exactly one tier through `bundleTierId` and lists only what the tier newly unlocks, so the archived base tiers accumulate (ordered by price). `Charity` (a donation add-on: soundtracks, art books, a cosmetic DLC) and `Upsell` (separately sold DLC or even a whole extra game) are optional add-ons which hold only their own products.
3. **Dates are exact.** `start`/`end` come straight from `startsAt`/`endsAt` (confidence 1.0).
4. **Ids need no resolver.** Every Steam product carries its `steamGameMetadata.steamAppId`, so there is no title search and no `unresolved:` marker; a Steam product without an app id fails the bundle loudly instead of being guessed. Products have no slug, so each item also carries the anchor `digiphile:<product ULID>`. Ebook (comic) bundles have no Steam ids and are archive-only.
5. **What becomes a list.** Base tiers are named after their USD price (`4.00 USD`) and ranked first, like dekudeals and isthereanydeal ranked them. The add-ons follow, charity before upsell, each by price, and are written as dependent tiers: `kind: charity|upsell` and `requires: [1]`, the lowest base tier they can only be bought with (the dependency is the maintainers' knowledge, the payload only has `type` and `price`). `--tiers highest` merges the add-ons you own into the collection of your highest owned tier (see `lists/README.md`). A bundle with one base tier and no add-on is a plain list.
6. **Dedup against the aggregators.** `crawler.find_covering_list` looks for an existing `lists/digiphile` list named exactly after the slug or the slugified title (`social-multiplayer` for `social-multiplayer-games-collection-digiphile`), ignoring the date prefix. The shared fuzzy/substring `existing_list_match` is deliberately not used: it hits older editions and prompts on a terminal. A match is backfilled through the shared `backfill_existing_lists` with the `digiphile:` ids it lacks and gets `digiphile` recorded in `crawlers`; its tier structure is kept as the aggregator wrote it (no add-on tiers). Otherwise a new list is written. The shared backfill never hands one id to two games, since aggregators list every DLC of a multi-DLC product separately and the fuzzy name match pairs them all with the one product.

Pipeline pieces:

- `models.py` - `DigiphileArchive`/`DigiphileTier`/`DigiphileItem`/`DigiphileDates`.
- `parser.py` - `flight_text`, `extract_bundle_slugs`, `extract_bundle`, `parse_bundle`, `bundle_slug`, `page_url`.
- `crawler.py` - `DigiphileHttpClient` (bounded-retry `httpx` wrapper), `crawl_digiphile_offers(fetch, ...)` with the usual injectable `fetch`/`log`/`on_offer`/`archive_root` conventions, and `write_digiphile_offer`.
- `migrations.py` - empty version-step lists (`DIGIPHILE_V1` is the first shape).

## Adding a new source (e.g. another bundle shop)

Use `humblebundle/` as the template for a source with resolver-based ID matching, or `dailyindiegame/` for one where the shop's own pages already give you a direct storefront ID. A new source is its own package `src/game_collections/sources/<source>/`, wired into the CLI the same way:

1. **Models** (`<source>/models.py`) — a strict Pydantic archive shape for the offer, analogous to `HumbleArchive`/`HumbleTier`/`HumbleItem` or the flatter `DigArchive`/`DigItem`. Base new models on `game_collections.models.StrictModel`/`NonEmptyString` so unknown fields and bad types fail loudly rather than silently rewriting bad data. Declare a `<SOURCE>_V1 = SchemaDateVersion(year, month, day)` constant plus `<Source>Versions = Literal[LEGACY_VERSION, <SOURCE>_V1]`/`<Source>CurrentVersion = Literal[<SOURCE>_V1]`/`CURRENT_VERSION`/`Versioned<Source>Archive = Versioned[<Source>CurrentVersion, <Source>Archive]` (see "Confidence-scored dates and the version envelope" above) instead of an embedded `schema_version` field — versioning lives in the on-disk envelope, not the archive model itself. If the offer has a start/end date, use `ScrapedTimestamp | None` (not a bare `datetime`) and record a real confidence for it, never assumed 1.0 without a verified page/API field.
2. **Parser** (`<source>/parser.py`) — turns the shop's raw page (embedded JSON, HTML, or an API response) into `(archive, source_payload)`, where `source_payload` is the relevant raw data worth preserving verbatim. Raise a source-specific parse error (mirror `HumbleParseError`/`DigParseError`) on anything unexpected instead of guessing. Don't assume page structure is fixed even within one site — DailyIndieGame's bundle title format alone has at least two variants; find a stable marker (a CSS class, a URL pattern) rather than matching exact wording.
3. **Resolver** (`<source>/resolver.py`, only if the shop's pages don't already give a direct storefront ID) — maps each product title to a qualified storefront ID (`steam:<appid>`, `gog:<id>`, etc). Reuse the existing storefront search machinery in `game_collections.search`/`StorefrontResolver`-style matching rather than reinventing per-store search. Persist reviewed decisions to a `config/<source>-store-ids.yml`-style resolution map (mirror `HumbleResolutionMap`/`render_resolution_map`) so re-crawling doesn't re-prompt for already-resolved titles, and record `unresolved:source:<source>:<key>` when nothing matches under `--non-interactive`. Skip this entirely if, like DailyIndieGame, the source page already links straight to a storefront ID.
4. **Crawler** (`<source>/crawler.py`) — a fetcher (mirror `HumbleHttpClient`'s bounded-retry `httpx` wrapper, or `DigBrowserClient`'s browser-based approach if the site needs one) plus a `crawl_*_offers(fetch, ..., archive_root=None, log=_NO_LOG, on_offer=None)` function that takes an **injectable `fetch` callable**, discovers or fetches explicit offers, and returns a report of successes and isolated per-offer errors (mirror `HumbleCrawlReport`/`DigCrawlReport`) so one bad page doesn't abort the whole run — and so tests never need a live network/browser. Log progress (`"Bundle x/y"`/`"Offer x/y"` and any per-item inner loop) via `log`, invoke `on_offer` as soon as each offer is ready, and skip expensive work via `sources.common.load_cached_archive` when `archive_root` is given and a valid cache entry exists (see "Progress logging, incremental writes, and resuming" above for the pattern to follow). A `write_*_offer(...)` function then atomically writes (reuse `sources.common.atomic_write`/`dump_json`/`render_game_list_yaml`) the normalized `archives/<source>/.../metadata.json` + `source.json`, and one `lists/<source>/...` YAML per purchasable tier/offer, each referencing its offer URL and archive files via `Reference`.

Then:

- **CLI**: add a new `@scrape_app.command("<source>")` in `src/game_collections/cli.py` next to the existing commands, following the same `--url`/`--lists-root`/`--archive-root`/`--refresh`(`--no-cache`) option shape, passing `log=typer.echo` and an `on_offer` closure that writes immediately (add `--resolution-map`/`--non-interactive` only if the source has a resolver stage).
- **Schema**: add a `write_<source>_schema(...)` in `src/game_collections/schema.py` and wire it into the `schema` command so `schemas/<source>-archive.schema.json` gets generated and drift-checked the same way the existing archive schemas are (see `tests/test_schema.py`).
- **Tests**: mirror `tests/test_humblebundle_crawler.py`/`test_humblebundle_parser.py`/`test_humblebundle_resolver.py` or `test_dailyindiegame_crawler.py`/`test_dailyindiegame_parser.py` — inline fixture HTML built from the real site's structure, fake `fetch` callables, no live network/browser access in tests.
